## Technical Analysis

### Option Comparison

| Option | Pros | Cons | Compatibility | Maintenance | Security |
|--------|------|------|---------------|-------------|----------|
| Native client activation only | Zero router code; uses existing Kiro matching | Non-deterministic selection; weak regression surface | Best for one client | Low | Depends on agent permissions |
| Structured deterministic router | Reproducible, testable, auditable | Regex/config maintenance; weak semantic understanding | Client-neutral core | Medium | Safe if route-only and fail-closed |
| LLM classifier | Handles paraphrase and nuance | Non-deterministic, model drift, harder to benchmark | Broad | Medium/High | Prompt injection and over-routing risk |
| Duplicate native skill copies | Immediate discovery everywhere | Content drift and conflicting fixes | High initially | High | Review surface multiplies |
| Canonical skills + thin/generated adapters | One semantic source; native discovery | Generator/link portability and adapter tests required | High | Medium | Adapters can enforce host policy |

### Detailed Evaluation

#### Structured router
- **Features**: logical route ID, skill ID, positive conditions, exclusions, explicit priority, fallback/abstain.
- **Integration**: a small pure function can consume JSON and return data; host adapters resolve skill IDs to paths.
- **Learning Curve**: Medium.
- **Performance**: trivial for 3-5 skills.
- **Security**: route-only output should never invoke a skill or tool. Validate schema, cap input length, contain resolved paths, and escape structured output.
- **Verdict**: Recommend for a bounded Kiro A/B pilot.

#### Native Kiro activation
- **Features**: metadata discovery and progressive disclosure built in.
- **Integration**: already supported at `.kiro/skills/*/SKILL.md`.
- **Learning Curve**: Easy.
- **Performance**: no local indexer needed.
- **Security**: skills share the selected agent's permissions.
- **Verdict**: Keep as baseline and fallback; do not replace until benchmark evidence shows a router benefit.

#### LLM classifier
- **Features**: semantic classification and natural-language explanations.
- **Integration**: no config parser, but every model/version is a new behavior surface.
- **Learning Curve**: Easy to prototype, hard to stabilize.
- **Performance**: adds latency and token cost.
- **Security**: task text can influence classifier behavior; requires an independent side-effect gate.
- **Verdict**: Avoid in the minimum experiment.

### Precise Architecture Observations

1. `MASTER-ROUTING.md` is the human orchestration contract; `routing.json` is the machine routing source. Documentation still duplicates the priority table, so coherence tests are essential.
2. Route scoring is additive by matched rule object, not weighted by keyword count. Priority is a tie-breaker. Confidence is only high/medium/low based on whether one or multiple route IDs matched; it is not calibrated to score margin.
3. Secondary routes preserve route-object encounter order, not priority order. Consumers must not treat secondary ordering as ranked without changing the contract.
4. The router emits Markdown containing the raw hint and writes to a caller-selected path. Newlines in a hint can forge fields for naive downstream parsers; a benign adaptation should return JSON and render Markdown only for display.
5. The local index's strongest reusable idea is the state split: installed/available, runtime available, registered, online, ready. The existing implementation is not fully neutral because it parses Claude and Codex registration, not Kiro, and may perform local HTTP probes.
6. The adapter layer is incomplete by native client standards. `AGENTS.md` is a generic instruction adapter and `CLAUDE.md` a Claude pointer, but native skill directory projections are absent.
7. Evidence, claims, ordered procedures, append-only transition logs, and work-item coverage are separate artifacts. This prevents prose summaries from becoming the only state.
8. The authorization gate precedes side effects and is independent of capability readiness. This is generalizable to deployments, external messages, destructive Git, database writes, and configuration mutation.

## Draft Output

### Executive Summary
The reusable core is a deterministic decision plane around native skills: structured routing config, a generated local capability view, benchmark fixtures, separate evidence/work state, and a hard side-effect gate. Reuse the separation of concerns, not the upstream scripts or domain workflows. Start with Kiro's existing native skill activation as the baseline and add a route-only classifier for five benign local skills.

### Recommendations (Prioritized)
1. **Pilot route-only classification**: no skill invocation and no tool execution; compare against native Kiro activation.
2. **Keep logical IDs client-neutral**: adapters resolve a skill ID to `.kiro/skills`, `.claude/skills`, or `.agents/skills`.
3. **Make authorization enforceable**: Kiro agent permissions remain the actual control; routing metadata is not a security boundary.
4. **Use append-only evidence and work state only where needed**: avoid a case-management framework for short tasks.
5. **Reject upstream bootstrapping and domain payloads**: no copied installers, MCP registrations, or offensive workflows.

### Minimum Benign Kiro Experiment
- Skills: `sql-server-table-reconciliation`, `validate-data`, `project-status-page`, `kpi-dashboard-design`, `sql-optimization`.
- Core files:
  - `experiments/skill-router/routing.json`: five logical routes, weighted terms, priority, and capability IDs.
  - `experiments/skill-router/benchmark.json`: 25 positive synthetic prompts, with five more abstain/overlap cases recommended before promotion.
  - `experiments/skill-router/router.mjs`: standalone route-only classifier, metadata baseline, and detection-only capability index.
- Output only: `{primarySkill, confidence, reason, secondarySkills, requiresApproval}`. No automatic activation.
- Gate: read-only routes may proceed; `project-status-page` requires explicit target path and write approval. Destructive/external/network actions are out of scope.
- Pass bar: all positive cases correct; all overlap/negative cases either expected or abstain; repeated runs identical; no filesystem/network mutations.
- A/B decision: keep the router only if it improves expected-selection accuracy over native Kiro activation without increasing false positives.

### Implementation Guidance
- Do not add dependencies; JSON parsing and regex matching are sufficient.
- Validate unknown keys, duplicate priorities, route/path containment, regex compilation, and benchmark coverage.
- Store evidence as compact JSON/Markdown records only for benchmark and decision outcomes.
- Do not create Claude/Codex adapters during the pilot.
